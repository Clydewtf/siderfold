# Локальная эксплуатация источников

Запуск источника намеренно сделан одноразовой локальной командой. Он не
запускает постоянный процесс, не включает расписание, не публикует программы и
не отправляет уведомления за пределы компьютера.

## Перед запуском

Используй Python-окружение проекта и примени миграции к локальной БД. Скрипт
`scripts/start-local.sh api` делает это сам, поэтому отдельная команда нужна
только если backend уже не требуется запускать. Docker назначает PostgreSQL
свободный порт, а не фиксированный `5432`; перед ручной миграцией нужно
получить этот порт и явно передать URL подключения.

Скрипт `scripts/start-local.sh` по умолчанию создаёт окружение вне репозитория
и при наличии нескольких Python выбирает Python 3.12. На текущем компьютере
это путь ниже. Если окружение находится в другом месте, задай
`SIDERFOLD_BACKEND_VENV` перед командой. После запуска скрипт печатает точный
путь как `Backend environment`.

```bash
cd backend
export PYTHON_BIN="${SIDERFOLD_BACKEND_VENV:-/private/tmp/siderfold-backend-venv-py3.12}/bin/python"
DB_PORT="$(docker compose --project-name siderfold port db 5432 | awk -F: '{print $NF}' | tr -d '\r')"
export DATABASE_URL="postgresql+psycopg://siderfold:siderfold@127.0.0.1:${DB_PORT}/siderfold"
$PYTHON_BIN -m alembic upgrade head
```

Если виртуальное окружение ещё не создано, сначала установи объявленные
зависимости бэкенда в изолированное окружение. Оно отделяет пакеты проекта от
системного Python macOS.

Проверь настроенные источники без обращения к ним:

```bash
$PYTHON_BIN -m app.sources.cli list
```

Прогони локальную тестовую фикстуру через полный защищённый контур:

```bash
$PYTHON_BIN -m app.sources.cli run fixture-catalog
$PYTHON_BIN -m app.sources.cli runs --source-key fixture-catalog
```

`run` получает блокировку PostgreSQL для источника. Параллельная команда не
ждёт и не запускает второй парсер: вместо этого она записывает
`skipped_locked` в журнал запусков.

## Проверка и публикация

Ниже — обычная последовательность для добавления проверенных данных в публичный
каталог. Она подходит для локальной операторской среды; автоматической
публикации или постоянного фонового запуска здесь нет.

1. Запусти приложение с токеном внутреннего доступа. Токен не нужно записывать
   в файл проекта: задай его в терминале, из которого запускается бэкенд.

   ```bash
   cd /path/to/siderfold
   export INTERNAL_API_TOKEN='длинный-случайный-токен'
   export INTERNAL_OPERATOR_ID='имя-оператора'
   ./scripts/start-local.sh api
   ```

2. В отдельном терминале подготовь доступ к той же локальной БД. Docker выдаёт
   свободный порт, поэтому не следует предполагать, что PostgreSQL доступен на
   `5432`.

   ```bash
   cd /path/to/siderfold/backend
   export PYTHON_BIN="${SIDERFOLD_BACKEND_VENV:-/private/tmp/siderfold-backend-venv-py3.12}/bin/python"
   DB_PORT="$(docker compose --project-name siderfold port db 5432 | awk -F: '{print $NF}' | tr -d '\r')"
   export DATABASE_URL="postgresql+psycopg://siderfold:siderfold@127.0.0.1:${DB_PORT}/siderfold"
   export INTERNAL_API_TOKEN='тот-же-токен'
   ```

3. Сначала запусти адаптер в `dry-run` и прочитай отчёт. Не запускай запись в
   БД, если формат источника неожиданно изменился, в отчёте есть ошибки или
   непонятные предупреждения.

   ```bash
   $PYTHON_BIN -m app.sources.cli dry-run potanin-competitions
   ```

   Во время обхода команда показывает безопасный ход работы в терминале: сколько
   карточек найдено, какая карточка или материал сейчас загружается и итоговые
   счётчики. Эти строки идут в stderr, поэтому итоговый JSON в stdout по-прежнему
   можно передать другой команде или сохранить отдельно. Для этого источника один
   HTTP-запрос может ждать до 45 секунд, а весь запуск ограничен 30 минутами. Если
   за это время не удалось дочитать карточки, отчёт завершится ошибкой и не создаст
   кандидатов; неуспевшие дополнительные материалы останутся ссылками с явным
   предупреждением для review.

   Для каждой ошибки validation отчёт содержит `row_number` и `resource_key` с
   URL карточки-источника. Открой этот URL, прежде чем исправлять или принимать
   кандидата. Несколько явно обозначенных циклов подачи — не ошибка: они остаются
   отдельными строками графика, а единый дедлайн сознательно не назначается.

4. Если отчёт приемлем, выполни управляемый запуск источника. Он сохраняет
   происхождение данных, метаданные исходных материалов и кандидатов для
   проверки, но не создаёт
   опубликованные программы сам по себе.

   ```bash
   $PYTHON_BIN -m app.sources.cli run potanin-competitions
   ```

5. Открой операторскую панель в браузере: адрес выводит
   `scripts/start-local.sh` после запуска API-режима. Обычно это
   `http://127.0.0.1:4191/operator.html`. Введи тот же
   `INTERNAL_API_TOKEN`, который был задан для backend. Токен остаётся только в
   памяти вкладки: после обновления страницы или выхода его нужно ввести снова.

   На странице:

   - **Очередь** открывает три представления одного кандидата. **Данные
     источника** показывают все структурированные поля адаптера и безопасную
     цепочку происхождения. **Предпросмотр карточки** показывает именно тот
     публичный вид, который получится после публикации. **Правки оператора**
     создают новую версию нормализованных полей, не изменяя raw capture или
     staging-запись.
   - **Качество** собирает предупреждения и блокирующие ошибки; ошибка не даёт
     принять запись.
   - **Запуски** показывает журнал адаптеров, import-батчи и разрешённые
     источники. Страница не запускает сбор: это отдельная осознанная команда.
   - **Discovery** помогает связать внешнюю ссылку с уже разрешённым источником
     либо оставить её на уточнении. Такая ссылка не создаёт программу сама.
   - **Публикация** позволяет архивировать опубликованную программу или вернуть
     архивированную, не изменяя таблицы напрямую.

   Для одинаково чистых кандидатов доступно массовое принятие. Оно показывает
   только открытые записи без проблем качества и с единственной причиной
   `candidate_ready`; сервер всё равно проверяет каждую запись и создаёт для неё
   отдельную запись аудита.

   Если нужно скорректировать данные, сначала сверь их с официальной страницей,
   затем открой **Правки оператора**, внеси только подтверждённые значения и
   укажи причину. Для блокирующей ошибки качества дополнительно отметь, какую
   именно ошибку исправляет эта версия. Исходное замечание не исчезнет: оно будет
   связано с версией правок в истории. «Запросить уточнение» меняет статус
   очереди, но сам по себе ничего не редактирует.

   В этой вкладке можно исправить все видимые части карточки: название,
   описание, сроки, суммы, график, тематики, регионы, условия участия,
   документы, материалы о победителях, официальные Telegram/VK-каналы и
   дополнительные текстовые разделы. Ссылка подачи заявки редактируется отдельно
   и в публичной карточке показывается кнопкой **Подать заявку**. В список
   материалов добавляй только самостоятельные документы, результаты или
   официальные каналы: обычная ссылка внутри фразы на странице источника не
   должна становиться отдельной карточкой. Первичный URL, raw capture и контакты
   остаются неизменяемыми доказательствами источника.

6. Если нужна быстрая проверка без браузера, посмотри созданный пакет импорта,
   очередь и детали конкретного кандидата в терминале.

   ```bash
   curl -sS -H "Authorization: Bearer $INTERNAL_API_TOKEN" \
     http://127.0.0.1:8000/api/internal/v1/ingestion-runs | python3 -m json.tool

   $PYTHON_BIN -m app.review.cli list

   export REVIEW_CASE_ID='<review_case_id>'
   $PYTHON_BIN -m app.review.cli show "$REVIEW_CASE_ID"
   ```

   Команда `app.review.cli` использует тот же локальный токен и выводит только
   краткую операторскую сводку: название, страницу источника, сроки,
   финансирование, причины проверки и историю решений. Она не показывает
   raw-capture, контакты или полный технический payload. Для редкой отладки
   полного JSON можно оставить `curl`, но добавь к нему `| python3 -m json.tool`.

   Предупреждение означает, что поле неполное или требует оценки; оно не подменяется
   выдуманным значением. Ошибка блокирует принятие. Для решения нужно сверить
   нормализованные поля с первоисточником и доказательствами кандидата.

7. Основной способ принять решение — операторская панель. Выбери запись,
   сравни её с официальной страницей, выбери действие и укажи причину. Каждое
   изменение требует причины и получает свой idempotency-ключ автоматически.
   Повторный щелчок не создаёт второе решение.

   Внутренний API остаётся доступен для автоматизированной или терминальной
   работы. Каждый запрос на изменение требует новый
   `Idempotency-Key`; повтор того же запроса с тем же ключом безопасно вернёт
   прежний результат. `accept` публикует подтверждённую программу, `reject`
   оставляет доказательства в истории, `needs_clarification` возвращает кейс на
   уточнение. `merge` допустим только при явном подтверждённом совпадении и
   требует `deduplication_match_id` из деталей кейса.

   ```bash
   export REVIEW_CASE_ID='<review_case_id>'
   export IDEMPOTENCY_KEY="accept-$(uuidgen)"

   curl -sS -X POST \
     -H "Authorization: Bearer $INTERNAL_API_TOKEN" \
     -H "Content-Type: application/json" \
     -H "Idempotency-Key: $IDEMPOTENCY_KEY" \
     -d '{"action":"accept","reason":"Данные сверены с официальной страницей источника."}' \
     "http://127.0.0.1:8000/api/internal/v1/review/cases/$REVIEW_CASE_ID/actions" | python3 -m json.tool
   ```

8. Убедись, что опубликованная программа появилась в публичном API и в каталоге,
   запущенном в API-режиме. Внутренние маршруты и технические данные проверки в
   публичный API не попадают.

   ```bash
   curl -sS http://127.0.0.1:8000/api/v1/programs
   ```

9. Если официальный источник перестал подтверждать программу, архивируй её,
   а не изменяй таблицы напрямую. Архивная карточка исчезает из публичного API,
   но история проверки и причина остаются в журнале аудита. Повтор того же запроса с
   тем же ключом безопасен.

   ```bash
   export PROGRAM_ID='<program_id>'
   export IDEMPOTENCY_KEY="archive-$(uuidgen)"

   curl -sS -X POST \
     -H "Authorization: Bearer $INTERNAL_API_TOKEN" \
     -H "Content-Type: application/json" \
     -H "Idempotency-Key: $IDEMPOTENCY_KEY" \
     -d '{"reason":"Официальная страница больше не подтверждает программу."}' \
     "http://127.0.0.1:8000/api/internal/v1/programs/$PROGRAM_ID/archive"
   ```

   Когда официальный источник снова подтверждён, используй новый ключ и
   `POST /api/internal/v1/programs/$PROGRAM_ID/republish` с той же структурой
   запроса. Повторно публиковать можно только архивированную программу.

Не изменяй канонические таблицы напрямую: это обойдёт ограничения,
идемпотентность и журнал аудита.

## Осознанное подключение расписания

`schedule-once` проверяет выражения расписания в UTC, запускает активные источники,
для которых наступило время, и завершается:

```bash
$PYTHON_BIN -m app.sources.cli schedule-once
$PYTHON_BIN -m app.sources.cli schedule-once --at 2026-09-01T04:15:00+00:00
```

Источники из репозитория имеют режим `manual`, поэтому сейчас команда никого не
выбирает. Не меняй сетевой источник на выражение расписания, пока не проверены
разрешённый доступ, ответственный и допустимая частота. После этого решения
планировщик хоста, например `launchd` или cron, может вызывать команду с
ограниченной периодичностью; сам репозиторий не должен создавать такую задачу.

Пример cron-записи, которую добавляет оператор, а не приложение:

```text
* * * * * cd /absolute/path/to/siderfold/backend && /absolute/path/to/python -m app.sources.cli schedule-once >> /absolute/path/to/siderfold-scheduler.log 2>&1
```

У каждого источника также есть `min_run_interval_seconds` в
`config/sources.toml`. Вместо слишком раннего второго запроса планировщик
записывает ограниченную по частоте попытку. Ограничения на количество запросов,
объём байтов, время одного запроса и всё время запуска продолжают действовать.

## Сбои и восстановление

Команда запуска повторяет только временные транспортные ошибки, HTTP 408/429/5xx
и недоступность БД. Она выполняет не более трёх попыток с ограниченно
увеличивающейся паузой. Ошибки конфигурации, нарушения белого списка, ошибки
парсера и валидации, а также другие HTTP 4xx считаются окончательными и не
повторяются.

Успешный пустой опрос записывается как `empty_success`. Любой отчёт с ошибками
получает статус `failed`, даже если в нём ноль записей. Сбой одного источника не
мешает тому же запуску планировщика попробовать следующий источник, для которого
наступило время.

При интерактивном `dry-run` или `run` команда выводит в stderr безопасные строки
прогресса, а финальный JSON-отчёт оставляет в stdout. Для неуспешного
управляемого запуска дополнительно выводится сокращённое JSON-уведомление с
ключом источника, ID запуска и кодами ошибок; в нём никогда нет тела ответа,
cookie, токенов или текста исключения. Вебхуки и внешние интеграции уведомлений
отсутствуют.

Если процесс прерван, PostgreSQL освобождает блокировку при закрытии сессии
БД. Следующий защищённый запуск помечает незавершённую операцию и подходящий
`IngestionRun` как прерванные/неуспешные перед новым запуском. Не очищай
блокировку вручную. Сначала посмотри журнал:

```bash
$PYTHON_BIN -m app.sources.cli runs --limit 50
```

## Хранение журнала

Строки запуска содержат время, результат, повторы, счётчики импорта, число
ошибок полей, свежесть и размеры двух очередей проверки. Это операционные
метаданные; `RawCapture`, `StagedRecord` и происхождение данных очистка журнала
не удаляет.

Срок хранения по умолчанию — 90 дней через
`SCHEDULER_JOURNAL_RETENTION_DAYS`. Очистка всегда запускается явно:

```bash
$PYTHON_BIN -m app.sources.cli prune-journal --retention-days 90
```

Запускай её только после проверки журнала и только для уже ненужной локальной
операционной истории. Команда никогда не выполняется автоматически.
