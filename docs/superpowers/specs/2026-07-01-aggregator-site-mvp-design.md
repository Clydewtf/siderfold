# Проектирование MVP сайта-агрегатора программ поддержки

## 1. Цель

Собрать первый рабочий MVP сайта-агрегатора программ поддержки. MVP должен показать идею продукта: единая база источников и программ, удобный каталог, быстрый поиск, фильтры и базовая аналитика по заранее подготовленным тестовым данным.

Сайт не является лендингом и не является продолжением текущего Python-парсера. Это отдельный frontend-модуль внутри репозитория, который позже можно будет подключить к backend, ручной панели загрузки данных или импорту из парсера.

## 2. Границы MVP

Входит в MVP:

- отдельная папка сайта в репозитории, например `site/`;
- frontend-only single-page приложение;
- вкладки `Главная`, `Источники`, `Все программы`;
- встроенные seed-данные;
- каталог источников;
- общий каталог программ;
- поиск, фильтры и сортировка на клиенте;
- раскрытие подробной информации о программе;
- мини-аналитика по seed-данным;
- базовая адаптивность для desktop и mobile;
- подготовка GitHub-этапов в implementation plan.

Не входит в MVP:

- backend;
- база данных;
- авторизация;
- админка;
- загрузка файлов пользователем;
- автоматический импорт из парсера;
- реальные регулярные обновления данных;
- полноценная BI-аналитика;
- отдельные публичные страницы для каждой программы.

## 3. GitHub и организация проекта

Implementation plan должен начинаться с GitHub и репозиторных шагов:

1. Проверить текущий `git status` и не смешивать работу сайта с посторонними untracked-файлами.
2. Проверить существующие remote и решить, нужен ли новый GitHub-репозиторий или новый remote для сайта.
3. Создать или выбрать ветку для MVP сайта.
4. Создать отдельную папку frontend-модуля, предположительно `site/`.
5. Добавить frontend-зависимости и конфигурацию только внутри `site/`, чтобы не ломать Python-парсер.
6. Закоммитить спецификацию отдельно от реализации.
7. После реализации закоммитить сайт и запушить в GitHub.

Если GitHub-репозиторий или remote еще не создан, план должен явно вынести это в отдельный шаг с проверкой доступа к `gh` или ручным созданием репозитория.

## 4. Архитектура приложения

MVP реализуется как frontend-only single-page приложение. Внутри одной страницы пользователь переключается между тремя основными вкладками:

- `Главная`;
- `Источники`;
- `Все программы`.

Все данные загружаются из локального seed-модуля или JSON-файла внутри frontend-папки. Фильтрация, поиск, сортировка, раскрытие карточек и расчет аналитики выполняются в браузере.

Рекомендуемые внутренние границы:

- слой данных: seed-данные и типы сущностей;
- слой вычислений: функции фильтрации, сортировки и аналитики;
- слой UI: вкладки, карточки, фильтры, аналитические виджеты, drawer/modal;
- слой форматирования: даты, суммы, статусы и человекочитаемые подписи.

Такое разделение позволит позже заменить seed-данные на API без переписывания интерфейса.

## 5. Модель данных

В MVP нужны два связанных уровня данных.

### Источник

Источник описывает фонд, платформу, университет, госпрограмму, акселератор или другой сайт, где публикуются возможности поддержки.

Минимальные поля:

- `id`;
- `name`;
- `type`;
- `description`;
- `topics`;
- `region`;
- `websiteUrl`;
- `logoLabel` или короткая текстовая метка;
- `trustNote` или краткое пояснение, почему источник полезен;
- `featured`.

Количество seed-источников: 8-12.

### Программа

Программа описывает конкретный конкурс, грант, стипендию, акселератор или другую возможность.

Минимальные поля:

- `id`;
- `sourceId`;
- `title`;
- `description`;
- `status`;
- `deadline`;
- `publishedAt`;
- `fundingAmountRub`;
- `fundingLabel`;
- `supportType`;
- `audience`;
- `topics`;
- `region`;
- `requirements`;
- `sourceUrl`;
- `documentUrls`;
- `featured`.

Количество seed-программ: 25-40. Данные должны включать разные типы поддержки, разные аудитории, несколько источников, программы с дедлайнами и без них, программы с указанным финансированием и без него.

## 6. Главная вкладка

Главная вкладка должна за 10 секунд объяснять, что делает сайт, и показывать масштаб тестовой базы.

Состав:

- короткий заголовок и описание агрегатора;
- мини-статистика: всего программ, всего источников, актуальных возможностей, ближайший дедлайн, максимальная сумма поддержки;
- быстрые переходы к вкладкам `Источники` и `Все программы`;
- блок `Что внутри`: источники, программы, сроки, суммы, тематики и ссылки на первоисточники;
- 3-4 заметные программы из seed-данных.

Главная не должна превращаться в маркетинговый лендинг. Это стартовый экран приложения: объяснение, состояние базы и вход в рабочие сценарии.

## 7. Вкладка источников

Вкладка `Источники` показывает, откуда агрегатор собирает программы.

Функции:

- сетка карточек источников;
- фильтр по типу источника;
- фильтр по тематике;
- счетчики программ на карточке источника;
- раскрытие выбранного источника прямо в интерфейсе;
- список программ выбранного источника;
- внешняя ссылка на сайт источника.

Карточка источника показывает название, тип, краткое описание, тематики, количество всех программ, количество актуальных программ и ссылку на сайт.

## 8. Вкладка всех программ

Вкладка `Все программы` является главным рабочим каталогом MVP.

Функции:

- поиск по названию и описанию;
- фильтр по тематике;
- фильтр по типу поддержки;
- фильтр по аудитории;
- фильтр по статусу;
- фильтр по дедлайну;
- сортировка по ближайшему дедлайну;
- сортировка по максимальной сумме поддержки;
- сортировка по новизне;
- сортировка по источнику;
- карточки программ;
- раскрытие подробностей программы через drawer или modal.

Карточка программы показывает название, источник, дедлайн, сумму или тип поддержки, аудиторию, тематики, статус, краткое описание и кнопку открытия первоисточника.

Подробный просмотр показывает расширенное описание, требования, ссылки на документы, ссылку на первоисточник и связанные данные источника.

## 9. Мини-аналитика

Мини-аналитика должна быть встроена в интерфейс и считаться из seed-данных.

Обязательные виджеты:

- распределение программ по источникам;
- распределение программ по типам поддержки;
- ближайшие дедлайны;
- доля программ с указанным финансированием;
- максимальная сумма поддержки;
- количество актуальных программ.

Аналитика должна помогать понять состояние базы, но не должна конкурировать с каталогом как отдельная BI-система.

## 10. Визуальный подход

После утверждения spec для реализации можно использовать `gpt-taste` как дизайн-направление. При этом сайт должен оставаться рабочим интерфейсом агрегатора, а не декоративной промо-страницей.

Визуальные требования:

- плотный, аккуратный dashboard-first интерфейс;
- качественный первый экран с описанием и статистикой;
- понятные вкладки;
- карточки источников и программ;
- хорошо читаемые фильтры;
- небольшие аналитические виджеты;
- адаптивная верстка;
- отсутствие горизонтального скролла;
- умеренная анимация, если она не мешает работе с каталогом.

LazyWeb можно использовать как внешний источник дизайн-референсов, если будет доступ или отдельные инструкции. Установленного LazyWeb-плагина в текущей среде нет.

## 11. Состояния и ошибки

MVP должен обработать базовые состояния:

- пустой результат поиска;
- пустой результат после фильтров;
- программа без дедлайна;
- программа без суммы финансирования;
- источник без актуальных программ;
- некорректная или отсутствующая внешняя ссылка в seed-данных.

Для frontend-only MVP эти состояния показываются как понятные сообщения в интерфейсе. Ошибки загрузки API не проектируются, потому что API в MVP отсутствует.

## 12. Проверка качества

Готовность реализации проверяется следующими пунктами:

- frontend собирается без ошибок;
- сайт запускается локально;
- вкладки переключаются без перезагрузки страницы;
- поиск возвращает ожидаемые программы;
- фильтры и сортировки работают на seed-данных;
- счетчики и аналитика считаются из тех же данных, что и каталог;
- карточка источника показывает связанные программы;
- карточка программы раскрывает подробности;
- desktop и mobile layout не ломаются;
- нет горизонтального скролла;
- существующий Python-парсер не затронут.

## 13. Будущие этапы вне MVP

После MVP можно добавить:

- backend API;
- постоянное хранилище данных;
- ручную панель добавления и редактирования источников;
- загрузку JSON/CSV через интерфейс;
- импорт из текущего или будущего парсера;
- модерацию данных;
- отдельные страницы источников и программ;
- пользовательские подборки и сохранение избранного;
- уведомления о дедлайнах.
